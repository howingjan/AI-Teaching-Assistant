# 课程资料驱动的 AI 补习教学助手

## 1. 文档目的

本文档定义一个面向海外院校补习老师的 AI 教学产品，从真实教学工作流出发，规划产品定位、MVP、技术架构、评测方式以及后续发展方向。

该项目不受当前 workspace 中已有代码框架限制。现有代码只作为实验素材；后续可以根据本规划重新设计项目结构、技术栈和部署方式。

## 2. 产品概述

### 2.1 产品定位

> 一个让补习老师能够基于课程资料，快速生成、审核和导出中文教学材料的 AI 教学工作台。

产品服务的不是泛化的“问答用户”，而是需要反复处理课件、作业、考试真题和课程要求的老师。

### 2.2 目标用户

第一阶段只服务老师本人，尤其是以下用户：

- 为海外大学课程提供中文补习的兼职老师；
- 每周需要覆盖完整知识点、重新组织讲解内容的老师；
- 需要讲解作业、历年真题并设计练习的老师；
- 需要在期末快速整理复习资料和 cheat sheet 的老师。

学生在第一阶段不直接登录系统。老师审核生成内容后，再在线下或其他教学渠道使用。

### 2.3 核心痛点

当前教学准备工作通常需要老师手动完成：

1. 从多份课件中查找本周相关知识点；
2. 将英文、偏学术的内容改写成中文基础讲解；
3. 设计适合学生水平的例子和课后练习；
4. 对照作业要求和评分标准讲解解题思路；
5. 期末重新浏览整门课并制作复习资料；
6. 在有限篇幅内整理两页 cheat sheet。

这些任务重复性高，但又不能完全交给通用大模型，因为课程材料、术语定义和作业要求必须准确，并且老师需要知道答案来自哪里。

### 2.4 产品价值

产品应当帮助老师：

- 减少资料整理和初稿撰写时间；
- 更稳定地覆盖课程知识点；
- 用更基础、适合中文学生的方式解释英文课程内容；
- 快速定位作业要求、评分标准和真题依据；
- 在生成内容中看到明确的课件页码引用；
- 保留老师审核、修改和决定最终内容的权利。

## 3. MVP 范围

### 3.1 MVP 目标

MVP 的目标不是做一个功能很多的教育平台，而是验证下面这个完整闭环：

> 老师上传一门课程的课件、作业和真题后，可以生成一份带来源引用、可编辑、可直接用于课堂的中文备课包。

### 3.2 MVP 工作流

```text
上传课程资料
    -> 解析和建立本地知识库
    -> 选择教学任务
    -> 输入教学目标、学生水平和课堂时长
    -> 检索相关课程内容
    -> 生成教学材料草稿
    -> 检查来源和内容完整性
    -> 老师审核、编辑
    -> 导出课堂材料
```

### 3.3 MVP 支持的任务

#### A. 本周备课包

输入：本周主题、课堂时长、学生基础和需要覆盖的章节。

输出：

- 本节课学习目标；
- 前置知识；
- 中文基础讲解；
- 英文专业术语及解释；
- 简单例子；
- 常见误区；
- 课堂互动问题；
- 课后练习题；
- 练习题提示和参考答案；
- 对应课件页码。

#### B. 作业与真题讲题

输入：作业题目、真题或题目截图，以及讲解目标。

输出：

- 题目考查的知识点；
- 解题需要的前置知识；
- 分步骤解题思路；
- 分层提示；
- 常见错误；
- 与评分标准的对应关系；
- 不直接代写的参考解题方向；
- 相关课件和作业要求的页码。

默认使用教学辅导模式，不生成可以直接作为学生提交物的完整答案。

#### C. 期末复习包

输入：整门课程资料和复习范围。

输出：

- 全课程知识点地图；
- 按章节组织的核心概念；
- 概念之间的依赖关系；
- 高频混淆点；
- 自测题；
- 真题对应知识点；
- 复习优先级建议；
- 每个结论的课程资料来源。

#### D. 两页 cheat sheet 草稿

输入：考试范围、纸张限制和允许携带的内容。

输出：

- 两页以内的结构化内容；
- 关键定义、公式、步骤和比较表；
- 适合考场快速查找的布局；
- 资料来源；
- 超出篇幅时的压缩建议。

最终内容必须由老师审核，并遵守课程和考试规定。

### 3.4 MVP 暂不包含

以下功能暂时不纳入第一版：

- 学生注册和学生端聊天；
- 自动批改和学习进度追踪；
- 全自动生成并发布整学期课程；
- 多租户 SaaS、账号体系和计费；
- 复杂的多 Agent 自主规划；
- 对所有扫描件、数学公式和复杂表格的完美 OCR；
- 无人工审核的自动发信或自动提交作业。

这些功能并非没有价值，而是应该在核心工作流被真实使用并验证之后再加入。

## 4. RAG 与 Agent 设计

### 4.1 为什么适合使用 RAG

RAG 适合这个场景，原因包括：

- 课件、作业要求和评分标准是回答的权威来源；
- 课程内容会因学校、学期和老师而变化；
- 老师需要看到答案对应的文档和页码；
- 系统需要识别“资料中没有提到”的问题；
- 不能把整套课程资料都放进每次模型请求中。

RAG 在这里主要负责事实依据和来源追踪，而不是替代教学设计。

### 4.2 第一版检索策略

第一版建议从本地、可解释的检索开始：

1. 按页读取 PDF、DOCX 或 Markdown；
2. 为每个文本片段保存文档名、文档类型、章节、页码和字符位置；
3. 使用页面和语义边界进行分块；
4. 使用 TF-IDF、BM25 或关键词检索返回 top-k 片段；
5. 将检索片段连同来源信息交给模型；
6. 要求模型只根据检索内容给出事实性结论；
7. 将引用绑定到具体片段，而不是让模型自由编造页码。

课程资料规模较小时，本地检索比一开始部署复杂向量数据库更容易调试、评测和演示。

后续可以加入 embedding 检索和混合检索，但必须通过离线评测证明它确实改善了结果。

### 4.3 Agent 的职责

这里的 Agent 不应是一个无边界、自主行动的聊天机器人。更合适的是一个受控的教学工作流 Agent，负责：

- 识别老师选择的教学任务；
- 收集教学目标、学生水平和课堂时长；
- 选择合适的提示模板；
- 调用课程资料检索工具；
- 组织多个生成步骤；
- 检查输出是否包含必要字段和来源；
- 标记需要老师确认的内容；
- 将结果格式化为可编辑、可导出的材料。

建议的工具权限只有：

- `search_documents`：检索课程资料；
- `get_document_structure`：查看章节、页数和文件信息；
- `find_related_questions`：查找相关作业题或真题；
- `validate_citations`：检查引用是否真实存在；
- `format_output`：生成 Markdown、HTML 或其他输出格式。

第一版不需要允许 Agent 自由访问互联网、发送消息、修改原始资料或自动提交作业。

### 4.4 结构化输出

每类教学任务都应有固定的数据结构，而不是只返回一段长文本。建议至少包含：

```text
任务类型
教学目标
目标学生水平
课堂时长
前置知识
核心讲解
示例
常见误区
课堂提问
练习题
提示或参考答案
来源引用
需要老师确认的内容
```

结构化输出可以提高界面展示、自动校验、导出和后续评测的稳定性。

## 5. 产品界面建议

第一版可以采用本地 Web 应用，技术实现可以选择 Streamlit、Gradio 或 React + Python API。技术选型不应先于产品验证。

主要页面或区域：

### 5.1 资料库

- 上传课程文件；
- 查看文件名、类型、页数和解析状态；
- 查看是否存在空页、扫描页、表格或图片；
- 删除或重新索引资料；
- 按课程或学期组织资料。

### 5.2 教学任务入口

不要只提供一个空白聊天框。应直接展示老师常用任务：

- 本周备课；
- 作业讲题；
- 真题分析；
- 期末复习；
- Cheat sheet。

### 5.3 生成结果区

- 展示结构化教学材料；
- 展开查看来源片段；
- 显示文档名和页码；
- 标记资料不足或需要人工确认的部分；
- 支持老师直接编辑；
- 支持导出 Markdown、HTML、Word 或 PDF。

## 6. 技术架构建议

```text
                +-----------------------+
                |   Teacher Workbench   |
                | upload / task / edit  |
                +-----------+-----------+
                            |
                +-----------v-----------+
                |  Teaching Workflow    |
                | task routing / schema |
                +-----------+-----------+
                            |
              +-------------v-------------+
              |      RAG Pipeline         |
              | retrieve / prompt / cite  |
              +------+---------------------+
                     |
       +-------------+-------------+
       |                           |
+------v------+             +------v------+
| Local Index |             | LLM Gateway |
| TF-IDF/BM25 |             | API/local   |
+------+------+             +-------------+
       |
+------v------------------+
| Course Document Store   |
| PDFs / slides / tasks   |
+-------------------------+
```

建议分层：

1. **文档层**：文件校验、解析、OCR、页面和章节识别；
2. **索引层**：分块、关键词索引、embedding 索引、元数据过滤；
3. **生成层**：RAG prompt、模型调用和结构化输出；
4. **工作流层**：按教学任务编排多个步骤；
5. **应用层**：资料管理、结果编辑、引用查看和导出；
6. **评测层**：检索、引用、事实性和任务完成度评测。

## 7. 可靠性与评测

### 7.1 评测问题集

使用真实课程资料建立一组人工标注问题，至少覆盖：

- 课件中明确出现的概念解释；
- 需要跨页或跨文档检索的问题；
- 作业要求和评分标准定位；
- 真题对应的知识点；
- 课件没有覆盖的资料外问题；
- 内容相互冲突的资料；
- 扫描页、表格和代码块；
- 需要生成练习和讲解的问题。

### 7.2 核心指标

- 检索 Recall@k；
- 引用文档和页码准确率；
- 资料外问题的拒答率；
- 无依据结论比例；
- 结构化字段完整率；
- 教学目标覆盖率；
- 端到端任务成功率；
- 平均响应时间；
- 单次生成成本；
- 老师编辑时间和接受率。

项目初期可设置以下目标值，实际数值必须通过评测得到：

- 引用页码准确率至少 90%；
- 资料外问题无依据回答率低于 5%；
- 关键结构化字段完整率至少 95%；
- 生成的备课包经过少量修改即可使用。

### 7.3 必须保留的失败案例

不要只展示成功截图。应记录：

- PDF 解析失败；
- 检索到了相似但错误的章节；
- 模型给出资料中没有的结论；
- 引用页码错误；
- 课件和作业要求不一致；
- cheat sheet 内容超出篇幅；
- API 超时或模型不可用。

面试中，说明如何发现这些失败、如何设计修复方案，通常比展示一个漂亮的聊天界面更有说服力。

## 8. 实施路线图

### Phase 0：产品验证

目标：确认真实用户愿意使用什么。

- 选择一门真实课程；
- 收集课件、作业、真题和评分标准；
- 记录一次完整备课流程的耗时；
- 手动整理 10 至 20 个典型问题；
- 明确老师最愿意交给 AI 的步骤，以及必须自己控制的步骤。

交付物：用户流程、任务清单、评测问题集和 MVP 范围。

### Phase 1：可引用知识库

目标：可靠地读取资料并找到正确内容。

- 支持 PDF、Markdown 和常见文本格式；
- 页面级解析和结构化元数据；
- 带文档名、章节和页码的分块；
- 本地关键词或 TF-IDF 检索；
- 检索结果可视化；
- 离线单元测试。

交付物：一个可以查询并显示来源片段的本地知识库。

### Phase 2：单任务教学生成

目标：先把“本周备课包”做完整。

- 固定任务表单；
- RAG 生成；
- 结构化输出；
- 来源引用；
- 资料不足提醒；
- 老师编辑和导出。

交付物：老师可以真实使用的一键备课流程。

### Phase 3：作业、真题和期末复习

目标：扩展到三个高价值教学场景。

- 作业讲题模式；
- 真题知识点映射；
- 分层提示；
- 期末知识点地图；
- cheat sheet 版面约束；
- 统一的任务评测。

交付物：覆盖完整补习周期的教师工作台。

### Phase 4：可靠性与展示版本

目标：让项目具备面试和作品集质量。

- 自动化评测报告；
- 引用校验；
- 成本和延迟监控；
- 失败案例库；
- 架构图和产品决策记录；
- 演示课程和可重复的 demo 脚本；
- 隐私、版权和学术诚信说明。

交付物：可以展示给面试官或潜在客户的完整项目。

## 9. 后续发展方向

### 9.1 学生端学习助手

当老师端工作流稳定后，可以开放有限的学生功能：

- 只基于老师选定资料进行问答；
- 根据学生水平调整讲解难度；
- 采用苏格拉底式提问；
- 逐步提示而不是直接给答案；
- 自动生成错题和复习建议；
- 将学生常见问题反馈给老师。

学生端必须有课程范围限制、引用展示和学术诚信边界。

### 9.2 自动批改与反馈

第二阶段可以支持：

- 识别答案使用的知识点；
- 对照 rubric 提供反馈；
- 区分概念错误、计算错误和表达问题；
- 生成下一步练习建议；
- 保存老师确认后的批改结果作为评测数据。

自动批改不应一开始就作为最终评分依据，初期应定位为老师的辅助反馈工具。

### 9.3 多模态资料理解

未来可加入：

- PPT 图表和流程图理解；
- 公式和代码识别；
- 作业截图解析；
- 白板照片转教学笔记；
- 图表、表格和 PDF 排版保真提取。

多模态能力应针对真实失败案例逐步加入，而不是为了展示技术而加入。

### 9.4 课程知识图谱

当资料数量增加后，可以建立课程知识图谱：

- 概念之间的先修关系；
- 知识点与作业题的映射；
- 知识点与真题的映射；
- 常见错误与对应补救练习；
- 每周课程与期末考试范围的关系。

这可以支持更好的复习路径和缺口分析，但不应替代第一版的简单检索。

### 9.5 个性化备课

系统可以根据老师的偏好学习输出风格，例如：

- 讲解深度；
- 中文和英文比例；
- 是否偏好例题；
- 课堂互动方式；
- 学生常见基础薄弱点；
- 习题难度分布。

个性化应优先通过可编辑模板、明确配置和老师反馈实现，而不是一开始训练专属模型。

## 10. 产品拓展策略

### 10.1 拓展顺序

建议按照以下顺序扩大范围：

```text
单老师本地工具
    -> 多课程管理
    -> 学生只读/受限使用
    -> 教师团队协作
    -> 教育机构 SaaS
    -> 多学科课程平台
```

每一步都应满足上一阶段的使用和可靠性指标后再推进。

### 10.2 从个人工具到 SaaS

当多个老师重复使用并产生明确需求后，再考虑：

- 用户和组织账号；
- 课程空间隔离；
- 资料权限管理；
- 云端索引；
- 用量和成本限制；
- 审计日志；
- 订阅和计费；
- 数据删除和导出。

本地部署版本和云端版本可以并存。涉及课程版权或学生隐私时，应允许机构选择数据存储区域和模型供应商。

### 10.3 商业化方向

可能的商业模式包括：

- 面向个人补习老师的订阅；
- 按课程或资料库收费；
- 面向补习机构的团队版；
- 定制课程知识库和部署服务；
- 面向学校或教育机构的私有化部署；
- 教学材料生成和课程运营工具的增值模块。

不要在没有验证留存、使用频率和付费意愿之前投入大量计费系统开发。

### 10.4 面向不同学科扩展

扩展到其他课程时，优先选择资料结构和教学任务相近的学科，例如：

- 数据科学；
- 计算机科学；
- 商业分析；
- 统计学；
- 信息系统。

不同学科需要独立的 prompt、评测集和术语规则。不能只替换课程资料，就假设同一套系统在所有学科都可靠。

## 11. 安全、隐私与学术诚信

产品设计必须明确以下边界：

- API key 不进入代码、日志或导出的教学材料；
- 原始资料默认保存在本地，并支持删除；
- 不上传包含学生个人信息的资料，除非用户明确理解风险；
- 对第三方模型的数据保留政策进行说明；
- 不把受版权保护的课程资料公开传播；
- 学生端默认提供提示和讲解，而不是代写作业；
- Cheat sheet 只在课程和考试规则允许时使用；
- 所有生成内容都标记为草稿，最终由老师审核；
- 重要结论必须有来源，找不到依据时明确告知用户。

## 12. 面试展示建议

项目展示可以围绕一个真实故事展开：

1. 老师每周需要花大量时间从英文资料制作中文课程；
2. 通用聊天机器人容易遗漏知识点、产生幻觉并且无法引用来源；
3. 因此设计了一个资料驱动的教师工作台；
4. RAG 负责课程事实，Agent 负责教学任务编排；
5. 每个输出都支持来源、审核和导出；
6. 通过人工问题集和引用准确率评测系统；
7. 根据失败案例逐步改进检索和输出结构。

建议准备以下演示：

- 上传课件、作业和真题；
- 查询一个课件中存在的问题并展示页码；
- 生成一份中文备课包；
- 展示资料外问题如何被拒绝；
- 展示作业如何输出分层提示而不是直接代写；
- 展示一个错误案例和修复前后的评测结果。

## 13. 成功标准

MVP 成功不等于“模型能回答问题”，而是满足以下条件：

- 老师可以完成从资料上传到材料导出的完整流程；
- 生成内容基本符合真实课堂需要；
- 关键事实可以追溯到课程资料；
- 对资料外问题不会无依据地自信作答；
- 老师审核和修改时间明显少于从零开始撰写；
- 系统在解析失败、检索失败和模型失败时有清晰反馈；
- 评测数据、失败案例和产品取舍可以被复现和解释。

最终产品方向可以概括为：

> 用 RAG 保证“讲的内容有依据”，用 Agent 组织“老师如何把内容教出去”，用评测和人工审核保证“生成结果真的能用于教学”。
